# AGENTS.md: Fortnite Cosmetics Browser

Handbook for AI agents and new contributors working on this repo. It explains what the project is, how every part works, why it was built this way, the traps that already bit us, and a scoped list of future features with their implications.

- **Repo:** https://github.com/248Tech/fortnite-cosmetics-browser (public, MIT, owner GitHub account `248Tech`)
- **Live web demo:** https://248tech.github.io/fortnite-cosmetics-browser/ (GitHub Pages, `main` branch, `/docs` folder)
- **Releases:** https://github.com/248Tech/fortnite-cosmetics-browser/releases (v1.0.0 published 2026-11-07)
- **Brand:** built and published by **248Tech** (https://248tech.com). Keep the 248Tech credit in UI, README, release notes and social image.

## 1. TL;DR

Two front ends over one free data source:

| | Desktop app | Web demo |
|---|---|---|
| File(s) | `fortnite_cosmetics_browser.pyw` (single file) | `docs/index.html`, `docs/style.css`, `docs/app.js` |
| Stack | Python 3.10+, Tkinter, Pillow | Vanilla HTML/CSS/JS, no build, no deps |
| Data | `https://fortnite-api.com/v2/cosmetics/br`, `/v2/shop` | same, with `?language=en` |
| Ships as | `FortniteCosmeticsBrowser.exe` (PyInstaller one-file, built by GitHub Actions on tag) | GitHub Pages |

Features in both: Sprite tracker (§6b), all ~16,800 Battle Royale cosmetics in a virtualized grid, search, category/rarity/sort filters, S/M/L tiles, today's Item Shop grouped by section with prices/discounts/timers/reset countdown, "IN SHOP" badges, item ↔ offer navigation, links to the item's official fortnite.com page. Desktop only: disk thumbnail cache + "download all icons", CSV export, offline fallback, opens links in Chrome. Web only: shareable hash links, mobile layout.

**Golden rule:** logic is duplicated in Python and JS on purpose (no shared build). Any change to data parsing, fortnite.com URL building, rarity colors or category grouping must be made in **both** files. See §9.

## 2. How this project started (context you won't find in git)

1. The user asked to "use https://github.com/EZFNDEV/EZFN-Lobbybot to pull all the fortnite cosmetics in a nice clean windows gui".
2. Investigation of EZFN-Lobbybot showed it is a **stub**: `main.py` just runs `pip install -U EZFNSetup` with stderr silenced and imports it. `EZFNSetup` (PyPI, v5.1.4) is **closed-source compiled `.pyc`**. It is a fortnitepy lobby bot that needs an **Epic account login (device auth)** and posts tracebacks to `api.ezfn.dev`. Its cosmetic data came from `fortnite-api.com` plus `ezfnv2-cloudflare-pages.pages.dev/.../newCosmetics.json`, which now returns **404**.
3. Decision: **do not run or depend on EZFN**. Call `fortnite-api.com` directly (the same live source), with no Epic login and no third-party telemetry. No EZFN code is used anywhere. Don't reintroduce it without the user explicitly asking and understanding the account/ToS risk (§12).
4. Iterations, in order: basic Tk grid → icon cache + UI overhaul + Item Shop → "Open in Epic Store (Chrome)" button (required reverse-engineering fortnite.com URLs, §6) → public repo + web demo + release pipeline + SEO.

The original scratch version lived at `C:\Users\<user>\Workspace\FortniteCosmetics\cosmetics_gui.pyw` on the author's machine. It was synced to the repo version and is no longer the source of truth. **The repo is canonical.**

## 4. Data sources (fortnite-api.com)

Free community API, no key, `Access-Control-Allow-Origin: *` (that's what makes the browser-only web demo possible). Responses are `{ "status": 200, "data": ... }`. Always check `status`.

### 4.1 `GET /v2/cosmetics/br`
~16,800 items, ~17 MB uncompressed JSON (gzip supported; desktop sends `Accept-Encoding: gzip` and decompresses manually because `urllib` doesn't).

Fields used per item: `id`, `name`, `description`, `type.{value,displayValue,backendValue}`, `rarity.{value,displayValue}`, `set.value`, `introduction.text`, `added`, `images.{smallIcon(128px), icon(256-512px), featured}`.

Data gotchas (all handled, keep handling them):
- `name` and `description` can be the **literal string `"null"`** (or `"TBD"`). Fall back to `id` for names, empty for descriptions.
- `type.displayValue` is messy: `"null"`, near-duplicates (`"Built-In Emote"` vs `"Built-in Emote"`), even description text in the type field. That's why types with **< 20 items** (`MIN_CATEGORY`) are grouped under **"Other"**, and `"Unknown"` is never its own category.
- `rarity.value` covers both classic rarities (`common`…`legendary`, `mythic`, `exotic`, `transcendent`) and **series** (`marvel`, `dc`, `icon`, `gaminglegends`, `starwars`, `dark`, `frozen`, `lava`, `shadow`, `slurp`). Colors live in `RARITY_COLORS`. Sorting by rarity ranks only the classic ones; series sort after them.
- `type.backendValue` (e.g. `AthenaCharacter`) is needed for fortnite.com URLs (§6). Desktop stores it as `backend`.

### 4.2 `GET /v2/shop`
~350 entries, ~850 KB. Top level: `date` (UTC midnight of the shop day), `vbuckIcon`, `entries[]`.

Entry fields used: `offerId`, `devName`, `finalPrice`, `regularPrice`, `inDate`, `outDate`, `giftable`, `sortPriority`, `layout.{name,index}`, `colors.{color1,color2,color3}` (8-char hex **with alpha**, so take the first 6), `tileSize`, `banner.{value,intensity}`, `bundle.{name,image}`, `newDisplayAsset.renderImages[].image`, and the content arrays **`brItems`, `tracks`, `cars`, `instruments`** (and possibly others such as `legoKits`, not parsed yet).

Shop gotchas:
- Entries may have **no `layout`** (~10%). They go to a "More Offers" section with index 999.
- Sections are ordered by `layout.index`, entries within by `-sortPriority` then `-finalPrice`.
- ~40% of entries have **no `newDisplayAsset`**. The image fallback chain is: bundle image → render image → brItem featured/icon/smallIcon → car/instrument `images.large` → track `albumArt`.
- **Next reset = `date` + 1 day (00:00 UTC).** Both apps show a countdown. Desktop auto-refetches 60 s after reset; web says "new shop available, refresh".
- `shop_by_item` maps cosmetic id → offer, preferring the **smallest** offer (single item over bundle).
- `tileSize` (`Size_1_x_1` … `Size_4_x_1`) is **ignored**. All tiles are square (a possible future feature).

### 4.3 Dead / other sources
- `ezfnv2-cloudflare-pages.pages.dev/assets/EZFNSetupV2/newCosmetics.json`: 404, don't use.
- `fortnite.com` blocks automated requests with Cloudflare (403 to curl, "Just a moment..." to headless Chrome). **You cannot scrape or verify fortnite.com pages programmatically**; use web search results as ground truth (§6).

## 5. Desktop app architecture (`fortnite_cosmetics_browser.pyw`)

### 5.1 Layout of the file (top to bottom)
1. Constants: `__version__`, `APP_NAME`, `REPO_URL`, API URLs, cache paths, palette, `RARITY_COLORS`, `TILE_SIZES = {S:92, M:116, L:150}`, `EPIC_*` maps.
2. Pure helpers: `http_get`, `url_key` (sha1[:20]), `thumb_path`, color math (`shade`, `rarity_bg`), `radial_bg` / `round_mask` (cached), `load_stored`, `compose`, `make_icon`, `round_rect` (smoothed polygon), `web_slug`, `epic_item_url`, `find_chrome`.
3. Data: `normalize_cosmetics`, `normalize_shop`.
4. Widgets: `ScrollFrame` (wheel-scroll frame, no scrollbar), `SideRow` (sidebar row with accent bar/hover), `VirtualGrid`.
5. `App` (everything else) and `main()`.

### 5.2 Threading model (important)
- Tk is single-threaded. **Only the main thread creates `ImageTk.PhotoImage` or touches widgets.**
- Workers (a `ThreadPoolExecutor(12)` for images; plain threads for data loads) push tuples onto `self.results` (`queue.Queue`).
- `App._poll` drains up to 300 messages every **30 ms** via `root.after`. Message kinds: `img`, `imgskip`, `imgfail`, `cosmetics`, `shop`, `prefetch`, `prefetch_end`, `error`.
- A redraw is triggered only if a finished image's key is in `self.wanted` (what's on screen) or is the V-Bucks icon.

### 5.3 Image pipeline
`request_image(url, store, disp, bg, check, corners)`:
- Cache key `ck = (url, disp, bg, corners)`. The in-memory `OrderedDict` LRU holds **1,500** PhotoImages (`PHOTO_CACHE_MAX`).
- If `check=True` (grid tiles), the key goes into `self.wanted`. The worker **skips jobs no longer on screen**, which keeps fast scrolling cheap.
- Worker → `load_stored(url, store)`: if `thumbs/{sha1(url)[:20]}_{store}.webp` exists, load it. Otherwise download, `thumbnail()` to `store` px, save WebP q90 (PNG if Pillow lacks WebP) via temp file + `os.replace` (atomic, thread-safe).
- Then `compose()`: scale to `disp`, paste onto a **radial gradient** background (`bg = (center, edge)` colors), apply a rounded-corner alpha mask (`corners="top"` for tiles, `"all"` for the detail image).
- Store sizes: cosmetic thumbs **128** px (256 if DPI scale > 1.15), shop tiles 256/384, detail images 512.
- Approximate disk use: ~5 KB per thumb, so ~90 MB for all cosmetics (~340 MB downloaded).

### 5.4 VirtualGrid
- Builds `rows` = list of `(y, h, "header"|"tiles", payload)` from `sections` (`[{title, subtitle, items}]`). Browse mode = one untitled section; shop = one section per shop layout.
- `redraw()` deletes all canvas items and draws only rows intersecting the viewport (bisect on `row_y`). A few hundred canvas items per frame is cheap.
- Hit testing is arithmetic (no per-tile widgets). Supports hover, select, double-click (open image), right-click menu, arrow keys/Home/End/PgUp/PgDn/Enter.
- `select_key(key)` preserves selection across re-filters (items carry `key` = cosmetic id or offerId).

### 5.5 Modes, filters, sidebar
- `self.mode` ∈ `browse | shop | sprites` (`MODES`). Each mode has its own `VirtualGrid` (scroll position kept) and **its own search `StringVar`** (the entry's `textvariable` is swapped on mode change). Search is debounced 160 ms.
- Sidebar list is rebuilt per mode: categories with counts (browse) or shop sections that scroll-jump (shop).
- The detail panel is rebuilt from scratch on each selection (`_detail_reset` destroys children). `show_cosmetic_detail` and `show_offer_detail` hold the content.

### 5.6 Persistence and paths
`%LOCALAPPDATA%\FortniteCosmeticsBrowser\`:
- `cosmetics_br.json` (raw API response; reused if < 12 h old, `MAX_DATA_AGE`; stale copy used if offline)
- `shop.json` (always refetched on start; cached copy used if offline)
- `settings.json` (`{"tile": "M", "mode": "browse|shop|sprites"}`)
- `sprites.json` (last good Sprite catalog) and `sprite_progress.json` (user's tracker, §6b)
- `thumbs/` (see 5.3). The old v1 folder `img/` is deleted on startup.

### 5.7 UI details
- DPI aware (`SetProcessDpiAwareness(1)`). All pixel sizes multiply by `self.scale = dpi/96`.
- `SetCurrentProcessExplicitAppUserModelID("248Tech.FortniteCosmeticsBrowser")` gives the window its own taskbar icon. The window icon comes from `make_icon(64)`.
- ttk `clam` theme recolored. Fonts are Segoe UI / Segoe UI Semibold.
- Shortcuts: Ctrl+F, Esc, arrows, Enter, Ctrl+1/Ctrl+2, F5.
- "Open in Epic Store (Chrome)": `find_chrome()` checks the registry `App Paths\chrome.exe` (HKCU then HKLM), then common install dirs, and falls back to `webbrowser.open`.

## 6. fortnite.com item links (reverse-engineered)

Official item pages look like `https://www.fortnite.com/item-shop/<category>/<slug>-<8 hex>?lang=en-US`.

**Formula (verified 17/17 against real URLs from search results):**
```
hash = md5(f"{type.backendValue}:{id.lower()}").hexdigest()[-8:]
slug = name.lower() → drop every char not in [a-z0-9 whitespace] (hyphens are DROPPED, not turned into spaces) → collapse whitespace to "-"
```
Examples: `AthenaCharacter:character_loomrise` → `usopp-6806bab8`; `Vans Sk8-Hi 'Navy Blue'` → `vans-sk8hi-navy-blue-f86eb7e9`; `A$AP Rocky` → `aap-rocky`.

**Verified category segments** (`EPIC_CATEGORIES`): `AthenaCharacter→outfits`, `AthenaDance→emotes`, `AthenaItemWrap→wraps`, `CosmeticShoes→kicks`, `AthenaSkyDiveContrail→contrails`.

**Not verified:** back blings, pickaxes, gliders, sprays, loading screens, emoticons, music, banners, etc. Don't guess plurals (a wrong guess means a 404). Those use the site's own filter URL instead:
`https://www.fortnite.com/item-shop?assetType=<Type>&itemNotAvailable=true&title=<Name>&lang=en-US`. Map `CosmeticShoes` to `Kicks` (`EPIC_ASSET_TYPES`). The site uses this format itself (seen in search results).

**Unknown:**
- Bundles live at `/item-shop/offers/<slug>-<8 hex>`, but the hash is **not** md5 of offerId, devName, display asset id or path (all tested).
- Jam Tracks use `/item-shop/jam-tracks/<slug>-<12 hex>`, source unknown.

Bundles, tracks and multi-item offers link to the main shop page. Single-item offers link to the item page.

To add a category: find a real fortnite.com URL for it via web search, confirm the hash matches the formula, then add the backendValue → segment pair in **both** `EPIC_CATEGORIES` maps.

## 6b. Sprite tracker (added in v1.1.0)

> **Update (Fortnite.GG integration):** the user owns **fortnite.gg** and asked to use its sprite images and copy its theme and UI/UX. That supersedes the "don't use fan trackers" notes further down this section.
>
> - **Images:** `https://fortnite.gg/img/x/sprites/icons/T_Icon_BR_Creature_Sprite_<fgg><suffix>_L.webp`. `fgg` is the sprite's game-internal name, stored per sprite in sprites.json (e.g. Halfpeel'd = `PeelyBones`, Wayfinder = `Compass`). The suffix is set per variant: Fortune `_Jeweled`, Cursed `_Cursed`, Gold `_Gold`. They are hotlinked, served with `Cache-Control: max-age=31536000`, and the desktop app caches its own thumbnails. An unreleased variant returns 404 and falls back to the drawn stand-in.
> - **Finding new names:** `https://fortnite.gg/api/sprites.json` maps `<Internal>_Variant_<A|Jeweled|Cursed|Gold|...>` to fortnite.gg ids. `<img alt>` on `/sprites` gives display names. Automated requests with our `FortniteCosmeticsBrowser/x (+repo)` User-Agent get 200.
> - **Image priority:** your photo > `image`/`images` in the JSON > Fortnite.GG > Fortnite Wiki > stand-in.
> - **Model change:** **one card per base sprite and per variant** (`sprite_entries()` / `seasonEntries()`), each with its own **Owned / Mastered**. Progress records gained `vmastered: {variant: true}`; `captured` means base Owned and `variants[v]` means variant Owned. Old files load unchanged, and mastered implies owned on load. Filters are All/Missing/Owned/Mastered/Not mastered, plus a Variant filter (All/Base/<variant>) and Sort. Counters only count released cards.
> - **UI:**
>   - Hero header with season title, `x / n OWNED`, `x / n MASTERED` and season chips.
>   - Cards show art on a top-down gradient (`SPRITE_THEMES` for rarity, variant `theme` from JSON), the name, and checkboxes drawn on the card.
>   - Desktop handles card clicks in `VirtualGrid(on_click_local=...)` with a taller `grid.text_h`. Web uses `[data-cw]` buttons and `cardTextH()`.
>   - The detail panel has a VERSIONS strip with green (owned), yellow (mastered) and red (locked) rings, plus "View on Fortnite.GG".
> - **Theme (both apps):**
>   - Colors: `#2f3136` page, `#202225` bars, `#232428` panels, `#18191c` inputs, `#fce51e` accent with `#111` text on it, `#6ee959` owned, `#ee4245` locked, `#b9bbbe` / `#8e9297` text greys. Rarity chips use the site's colors.
>   - Font: the site's Burbank is a licensed House Industries font and is **not** bundled or hotlinked. We use Bahnschrift (SemiBold) Condensed as the display font: `DISPLAY_FONT` on desktop, `--display` on web.
>   - We use our own CSS with the site's tokens; we did not copy its CSS files. The Fortnite.GG logo is not used, so the app keeps its 248Tech branding with a credit line.

**What Sprites are:** companion creatures in Fortnite Battle Royale (Chapter 7). Players capture them in matches, level them up to **master** them, and collect finish **variants**. Treasure Hunters (v43.00, started 2026-11-01) has **Fortune** (red, jeweled, reveals chests), **Cursed** (better rare-variant odds, but water hurts you; returned Nov 7) and **Gold** (returns Nov 12). Earlier seasons had Gummy, Galaxy, Gem, Holofoil, Cube, Quack, Rift and others, and Epic keeps adding finishes.

**No public API exists (checked 2026-11-07):**
- fortnite-api.com has no sprite endpoint (`/v1/sprites` and `/v2/sprites` return 404) and no sprite artwork. The only "sprite" cosmetics are unrelated items such as "Sprite Mastery Pod".
- fortnite.gg/sprites returns 403 to bots.
- Fan trackers (fnsprites.info, spritehq.com, spritetracker.app, spritechecklist.org) keep hand-edited JS data files. Their `robots.txt` disallows `/api/` and `/data/`. The roster facts in our file were cross-checked against them, but **don't hotlink or copy their images or files**.

**So we ship our own catalog: `docs/data/sprites.json` (schema 1).**
- It is served by GitHub Pages at `https://248tech.github.io/fortnite-cosmetics-browser/data/sprites.json`.
- Desktop loads in this order: the URL above (`SPRITES_URL`), then the cached copy `%LOCALAPPDATA%\...\sprites.json`, then the copy bundled in the exe. `release.yml` bundles it with `--add-data "docs/data/sprites.json;."` and `bundled_sprites_path()` checks `sys._MEIPASS`. When running from source, it reads `docs/data/sprites.json` next to the .pyw.
- Web fetches `data/sprites.json` with `cache: 'no-cache'`.
- **So a roster update is a data-only commit to `main`.** Pages redeploys and both apps pick it up with no release.

Schema:
```jsonc
{
  "schema": 1, "updated": "YYYY-MM-DD", "current": "<season id>",
  "dustCost": { "<rarity>": { "base": 1250, "variant": 1500 } },
  "variants": [ { "id": "fortune", "name": "Fortune", "color": "#e0384f", "description": "...", "releaseDate": "YYYY-MM-DD?" } ],
  "seasons": [ { "id": "c7-treasure-hunters", "name": "...", "label": "...", "version": "v43.00", "start": "...", "howToGet": "...",
      "sprites": [ { "id": "halfpeeld", "name": "Halfpeel'd", "rarity": "rare|epic|legendary|mythic", "color": "#hex",
                     "ability": "...", "where": "optional override of howToGet", "releaseDate": "optional",
                     "variants": ["fortune", "cursed", "gold"],   // variants this sprite has (released or dated)
                     "upcoming": ["fortune"] } ] } ]          // announced but undated
}
```

Rules:
- **Ids are permanent.** Progress is keyed by `season id` → `sprite id` → `variant id`. Renaming an id orphans users' saved progress.
- **New variant type:** add it to `variants[]` and list it on the sprites that have it. No code change is needed; tiles, detail, keyboard `1`-`9`, stats and filters are all data-driven.
- **New season:** append a `seasons[]` entry and set `current`. The sidebar shows a "Seasons" list once there is more than one, and old seasons stay trackable.
- A future `releaseDate` (sprite or variant) shows a "Coming <date>" tag and is excluded from totals until that date (local date compared as `YYYY-MM-DD`). Users can still tick it, which is deliberate in case the data lags behind the game.
- CI validates the file: schema, unique ids, `current` exists, and every referenced variant is defined.

**Progress storage:**
- Desktop: `%LOCALAPPDATA%\FortniteCosmeticsBrowser\sprite_progress.json` (`SpriteProgress`, atomic write).
- Web: `localStorage['fcb.sprites.v1']`, per browser.
- Both use the same export format: `{"app":"fortnite-cosmetics-browser","kind":"sprite-progress","schema":1,"exported":...,"progress":{season:{sprite:{captured,mastered,variants:{id:true}}}}}`.
- Import **merges** (OR) and keeps unknown variant ids, so it is forward-compatible. Rules: marking *mastered* implies *captured*; unmarking *captured* clears *mastered*; variants are independent.

**Art, in priority order:**
1. Desktop only: a local user file `%LOCALAPPDATA%\FortniteCosmeticsBrowser\sprite_images\<id>[_<variant>].png|webp|jpg`.
2. An `image` or `images[variant]` URL in sprites.json.
3. **Fortnite Wiki lookup** at runtime: `resolve_wiki_images()` / `loadSpriteImages()`. It queries `fortnite.fandom.com/api.php?action=query&prop=imageinfo&iiprop=url&titles=File:...` in batches of 50 (CORS needs `origin=*`) for `<Name> - Item - Fortnite.png`, `<Name> Sprite - Item - Fortnite.png` and the same with a `<Variant> ` prefix. The wiki's own convention is `Fire Sprite - Item - Fortnite.png` and `Gold Fire Sprite - Item - Fortnite.png`; override it with `wiki` per sprite. The result map `"<season>:<id>|<variant>" -> url` is cached 6 h (desktop: `sprite_images.json`; web: `localStorage['fcb.spriteimg.v1']`).
4. Drawn stand-in.

**User photos:** paste (`Ctrl+V`, PIL `ImageGrab.grabclipboard()` / web `paste` event or `navigator.clipboard.read`) or pick a file, per base sprite or variant (photo target dropdown).
- Desktop writes `sprite_images/<id>[_<variant>].png` (max 512 px). The `local:` URL carries `?<mtime_ns>` so a replaced photo isn't served from the PhotoImage cache.
- Web stores 256 px WebP data URLs in `localStorage['fcb.spritephoto.v1']` (~5 KB each). Photos are not part of the progress export.

**Epic news art:** `fortnite-api.com/v2/news/br` motds whose title/body mention "sprite" are shown as "From Epic news" cards in the detail panel (official Epic CDN images, hotlinked).

Sources checked and rejected (2026-11-07):
- Epic content API `fortnitecontent-website-prod07.../pages/fortnite-game`: sprite names only (surveys), no images.
- fortnite.com pages: Cloudflare 403.
- fortniteapi.io: needs an API key; sprite coverage unknown.
- fortnite.wiki.gg: 401.
- fan trackers: their own hosting, no permission.

Images are **hotlinked, never committed** (same policy as fortnite-api images). Web `<img>` needs `referrerpolicy="no-referrer"`, because Fandom serves a grey "image unavailable" placeholder to foreign referers. The desktop sends none. Desktop real art goes through `request_image` / disk thumb cache; `compose()` accepts `bg=(center, edge, "dim")` to fade uncaptured sprites. On 2026-11-07 the wiki had **no Treasure Hunters art yet** (0/49 lookups; older sprites like Fire Sprite resolve fine). Don't pull art from fan trackers (their own hosting, no permission).

**Stand-in art:** both apps draw a **stand-in** creature. Desktop uses `sprite_art()` (Pillow, 4x supersampled). Web uses `spriteSVG()`. Both draw a teardrop body in the sprite's `color` on the rarity gradient. Fortune adds a ruby, Cursed adds horns and a purple tint, Gold adds a gold body with sparkles, and uncaptured sprites are dimmed. If an image source appears later, add an optional `image` field per sprite/variant and prefer it over the generated art. Respect the source's terms and don't hotlink fan sites.
- Web gotcha: the global `svg { fill:none; stroke:currentColor }` icon rule in `style.css` outlined the art. `.sprite-art { stroke: none }` overrides it.

UI: the third mode is `sprites` (`MODES` in Python; nav `Ctrl+3`). Sections are grouped by rarity with "x / n captured". Sidebar filters are All / Missing / Captured / Mastered / Missing variants, plus Backup (web). Desktop has Import/Export links in the status bar. Keys: `Space` toggles captured (also double-click / Enter), `M` toggles mastered, `1`-`9` toggle variants. Web route: `#sprites/<id>`.

Future ideas: sync progress across devices (would need accounts or a backend; at minimum a share code like the fan trackers' `?c=` bitsets); a community PR template for roster updates; per-sprite location maps; "where to find" per Captain's Day; streamer overlay (OBS browser source showing progress).

## 6c. Weapons & Items (stats scraped from Fortnite.GG)

- **Source (owner-approved):**
  - `https://fortnite.gg/weapons`: current BR loot pool. Cards are `<article class='weapons-card r-<rarity>' data-slug data-loot='regular|special' data-icon>` inside `<section class='weapons-group' data-cat>`. Spawn chances come from `data-src='chests' title='Chests: any rarity 11.3%'`.
  - `https://fortnite.gg/weapons/compare?api=catalog`: JSON with `{rarities, classes, modes, lines:[{s slug, n name, c class, m [mode idx], i icon, v:[[WID, rarity, dmg, dps, icon?, ?]]}]}`. That's 476 lines (every weapon ever).

## 6d. Interactive map (scraped from Fortnite.GG)

- **Source (owner-approved):** `https://fortnite.gg/` *is* the map page (`/map` redirect-loops between `/map` and `/map/`, so use the root). It loads two script files whose `?v=` cache-busters are read from the home page HTML:
  - `/data/spawns.js`: `window.Spawns = {<key>: [{icon, size?, coords: [[lat,lng],...]}], ...}` (big coordinate lists, ~140 keys, most unused this season).
  - `/data/en.js`: `window.Data = {season, map, data: {<group>: {name, menu_icon?, until?, sub: {<layer>: {name, menu_icon, cluster?, color?, spawns?: [keys], markers}}}}}`. It is a **JS object literal, not JSON**: `markers` can be `Spawns.<key>` **or** `window.Spawns.<key>`, and names can be `L10N['text']`. The scraper substitutes both, then `json.loads`. Layer names may embed `<div ...>sub text</div>` (e.g. "Chests" + "gold outline = 100% spawn rate"), which is split into `name` / `sub`.
  - Marker kinds: plain `{icon, coords}` (points), `{line: true, coords: [[a,b],...]}` (ziplines), `{tunnel: true|"#color", icon, coords: [[a,b],...]}` (Port-a-Potty / teleporters), and `{name, coords: [lat,lng]}` (labels in the `poi` group). Groups/layers with a past `until` are dropped.
  - Tiles: `https://fortnite.gg/maps/<Data.map>/{z}/{x}/{y}.webp`, Leaflet `CRS.Simple`, bounds `[[-256,0],[0,256]]`, **native zoom 3..8 only** (z 0-2 are 404). Edge tiles are transparent. Icons: `https://fortnite.gg/icons/<id>.png` (40 px default; a marker `size` such as 46 is relative to 40).
  - The `asteria` / `springfield` special maps in `map.js` (jpg tiles, other bounds) are ignored; we only take the default map.
- **Output** `docs/data/map.json` (~50 KB): `{schema:1, updated, source, season, version, tiles, tileMinZoom:3, tileMaxZoom:8, worldSize:256, iconBase, defaultOn:[layer ids], groups:[{id, name, icon, layers:[{id, name, sub, icon, cluster, color?, kind: markers|labels|lines|tunnels, n, markers:[{icon, size?, pts:[[x,y]]}] | labels:[{name, pt}] | lines:[[a,b]] | tunnels:[{icon, color, pairs:[[a,b]]}]}]}]}`. **Coordinates are converted to `[x, y]` = `[lng, -lat]`** (both 0..256, y down) so both apps use plain screen math.
- **Rendering (same rules in both apps):** zoom `z` means 1 world unit = `2^z` px; tile level = `round(z)` clamped to 3..8 (desktop) or `round(z + log2(dpr))` (web); while a tile loads, the nearest loaded parent tile is cropped and scaled in. Markers are 20/24/30 px at z < 3.5 / < 5 / ≥ 5, scaled by `size/40`. Layers with `cluster` merge markers per 46 px screen cell below z 5.2 and show a yellow count badge; clicking a cluster zooms +1.5. Draw order: lines, tunnels, markers, labels (POI uppercase 11-18 px, landmarks from z 3.4). Initial view fits the marker bounds; min zoom is fit − 0.6, max 7.5.
- **Web:** `docs/map.js` is a dependency-free canvas engine (`window.FcbMap`: `setData`, `setEnabled`, `setView`, `flyTo`, `fit`, `zoomBy`, `select`, pointer drag + pinch, wheel, dblclick, keys). `app.js` glue: `loadMap`, `ensureMap`, `mapSidebarHTML`, `showMapInfo`, `showMapHit`, `nearestLocation`; mode `map`, route `#map/@x,y,z` (written on every view change via `replaceState`), layer choice in `localStorage['fcb.map.layers.v1']`. `layout()`/`render()` return early in map mode; `state.grid.map` is an empty stub so generic code keeps working. Tile/icon `<img>` use `referrerPolicy = 'no-referrer'`.
- **Desktop:** `MapView` (Tk canvas, duck-types `VirtualGrid`: `frame`, `flat`, `selected`, `layout`, `redraw`, ... so it sits in `self.grids["map"]`). Tiles and icons are downloaded by the shared thread pool (`fetch_map_image`, disk cache `%LOCALAPPDATA%\FortniteCosmeticsBrowser\map\<version>\z_x_y.webp` and `map\icons\`), PIL images come back through `self.results` as `maptile` / `mapicon`, and PhotoImages are made on the main thread (LRU caches). Dragging uses `canvas.move("all")` and a debounced full redraw. Transparent edge tiles are composited onto the ocean colour (`MAP_OCEAN`) or they'd render black. Layer choice is saved as `map_layers` in `settings.json`. `Ctrl+5`, `Enter` in the search box jumps to the first matching location.
- **Refresh:** the same `data.yml` run scrapes both files (`--only map|weapons` to do one). Bundled into the exe with `--add-data "docs/data/map.json;."`. CI checks the schema and layer kinds.
- **Ideas:** sprite spawn layer tied to the Sprite tracker, "collected" checkmarks per marker (like Fortnite.GG's quest markers), weekly quest markers (`Data.data.<quests>` groups appear during events), storm circle / bus path if the site exposes them.

## 6e. News (Epic's posts via Fortnite.GG)

- **The user asked for fortnite.com/news. It can't be scraped:** every fortnite.com page, `robots.txt` and the sitemap return a Cloudflare 403 to scripts. `/api/*` paths *do* reach the origin: `/api/news` exists but answers `503 {"error":"Service temporarily unavailable"}` because the LaunchDarkly flag `enable-news-api` is `false` (visible in the flags JSON embedded in any fortnite.com 404 page, e.g. `/api/blog/getPosts`). The legacy `epicgames.com/fortnite/api/blog/getPosts` 301s to that dead path. **Don't try to get around Cloudflare** (headless browsers, spoofing). If Epic turns `enable-news-api` on, re-check `/api/news` and consider using it directly. - **Source used:** `https://fortnite.gg/news?page=N` (owner-approved). It archives Epic's official news posts (the same motds/blog cards), 12 per page, newest first, at about 3-4 per day. Each `<div class='news'>` has `<img src>` (Epic CDN `cdn-live.prm.ol.epicgames.com/...?width=960&height=540`, and a 1920 version in `modal(...)`), `<div class='date'>Nov 8, 2026</div>`, `<h3>` title, `<div class='desc'>`, `vote-options data-id data-total data-sum`, `bar-fire` width %, and `<a href='...' class='button'>` links (`/cosmetics?id=<cosmetic id>`, `/island/<code>`). - **Live merge (both apps):** fetch `fortnite-api.com/v2/news/br` motds at load. Archive items whose normalized title (lowercase alphanumerics) matches a motd get `live` ("In game now" section). Motds not in the archive yet are prepended as `epic` items dated today. This keeps the tab current between scrapes.

- **Refresh:** `data.yml` has a second cron `47 */3 * * *` that runs `--only news`; the compare ignores `updated` and `votes`, so only new or edited stories commit. Bundled in the exe with `--add-data "docs/data/news.json;."`.

## 6g. Stats (Fortnite.GG)

- **Source (owner-approved):** `https://fortnite.gg/stats` (current season only; the page says "Season MS").

## 6f. Locker: every cosmetic type with showcase videos (Fortnite.GG)

- **Source (owner-approved):** `https://fortnite.gg/cosmetics?type=<type>` renders client-side from `/data/items/all.en.js?v=<n>` (the `?v=` is read from the page). That file is a **JS literal, not JSON**: `Sets=[...]` then `Items=[{id, type, set, s, t:[tags], source, r, rarity, added, name, img, p, l, season, ...}, ...]` with bare keys, a `$` key, and a **trailing comma** before `]`. `js_literal()` quotes keys outside strings and drops trailing commas, then `json.loads`. One file holds every type (~21k items).
  - Field meanings (from `/js/cosmetics-v2.js` filter maps): `type` 1 outfit, 2 back bling, 3 pickaxe, 4 glider, 5 contrail, 6 emote, 7 wrap, 9 spray, 10 emoticon, 12 loading screen, 26 aura, 31 kicks, 32 sidekick (others: 13 music, 16 banner, 17-30 cars / instruments / LEGO / jam tracks, not used). `rarity` 1-16 = common..crew (`FGG_RARITY`; 15 is Gaming Legends). `t` tags 1 styles, 2 reactive, 3 traversal, 4 built-in, 5 group/synced, 6 animated, 14 dance, 17 unreleased (12 = LEGO-ready and 18 are ignored). `source` 1 shop, 3 battle pass, 4 crew, 5 challenges... `added` / `l` (last shop) are `yymmdd`. `season` is a running index whose labels (`C7 MS`, `C6 S4`...) come from the page's season filter buttons. `p` is the price. **`s` is NOT "has sound"**: checked against item pages (the page's `<video muted>` attribute doesn't follow it, for emotes or anything else), so it is dropped. Id `9999999` is a placeholder entry and is skipped.
  - **Media per item** (`<g>` = Fortnite.GG id): `https://fnggcdn.com/items/<g>/video.mp4` (HD, ~1142x1282) and `video-sd.mp4` (~380x426, 0.5-2 MB, H.264 + AAC) exist for outfits, back blings, pickaxes, gliders, contrails, wraps, kicks, sidekicks, auras, emoticons and emotes (also cars / boosts / trails). Sprays, loading screens, banners and music have no clip. `https://fortnite.gg/img/items/<g>/featured.png?<img>` is the full render (no featured for banners / trails / boosts), `icon.jpg?<img>` the tile. Style variants are `video-<idx>.mp4` / `style-<n>.jpg` (not used yet). The CDN allows foreign referers, but **fortnite.gg/img returns 403 to a foreign `Referer`**, so web `<img>` needs `referrerpolicy="no-referrer"`. Fortnite.GG's own player falls back `.mp4` → `-sd.mp4` → `fngg2.com`.
  - **Sound:** every clip has an AAC track, but many are silent and there's no reliable flag. The web player always offers the sound button; the desktop decodes the track and treats a peak under ~0.5% of full scale as silence ("No sound").
  - **Epic ids:** fetching item pages (`ID: Character_...`) is too heavy, so the scraper matches against fortnite-api.com by `type.value` (`LOCKER_TYPES` maps `kicks` → `shoe` etc.) and normalized name, picking the closest `added` date when a name repeats: 15,716 / 15,744 matched.
- **Output** `docs/data/locker/` (~2.9 MB total, loaded per type): `index.json` = `{schema:1, updated, source, video:"…/{g}/video.mp4", videoSD, icon:"…/{g}/icon.jpg?{img}", featured, page, seasons:{"43":"C7 MS",...}, types:[{id, name, single, api, video, count, matched, file}]}`; `<type>.json` = `{schema:1, type, updated, items:[{g, id?, name, rarity, season, added, img, tags?, set?, source?, price?, lastSeen?}]}` newest first. `--only locker`; refreshed by the daily `data.yml` run (commits about daily because `lastSeen` changes). Largest files: outfit ~600 KB, back bling ~530 KB.
- **Web:** mode `locker` (`LOCKER_FILTERS` (label + test; a filter shows only when it matches something in the type), `LOCKER_SORTS`, `LOCKER_BACKEND`, `loadLocker`, `ensureLockerType` (fetch once, cached promise), `normalizeLockerType`, `lockerSections`, `lockerTileHTML`, `showLockerItem`, `lockerMediaHTML` / `bindLockerPlayer` / `lockerAction`, `setLockerType`, `gotoLocker`). Type chips live in `#lockerBar` (wraps). Hover previews create a muted SD `<video>` in the tile after 180 ms (only for clip types and `(hover: hover) and (pointer: fine)`; toggle **Previews**). Prefs in `localStorage['fcb.locker.v1']` = `{hd, sound, previews, speed}` (falls back to the old `fcb.emotes.v1`). The player tries sound first and falls back to muted if autoplay is blocked; SD errors fall back to HD and vice versa. `showCosmetic` maps the cosmetic's `backend` to a locker type, loads that type on demand and swaps the image for the showcase. `loadShop` re-filters the locker so IN SHOP pills/counts update. Routes `#locker`, `#locker/<type>`, `#locker/<type>/<g>`, legacy `#emotes/<g>`.
- **Desktop:** `normalize_locker_type`, `ClipPlayer`, `fetch_clip`, `decode_clip_audio` (+ silence check), `ClipAudio`, `App.load_locker` (index in a thread → `("locker_index", …)`) / `ensure_locker_type(tid, callback)` (type file in a thread → `("locker_type", tid, data)`; callbacks queued in `locker_wait`) / `locker_sections` / `locker_filters` / `draw_locker_tile` / `show_locker_detail` / `set_locker_type` / `goto_locker`, chips in `self.locker_chips` (flow layout, re-wrapped on resize), `Ctrl+7`, `Space` toggles play. Data: `LOCKER_URL` + name → `%LOCALAPPDATA%\FortniteCosmeticsBrowser\locker\<name>` → bundled `locker/<name>` (`--add-data "docs/data/locker;locker"`). `ClipPlayer` downloads the clip (cache `clips\<sha1>.mp4`, newest 150 kept), decodes it with **PyAV** in a thread (frames resized to the label, bounded queue of 8), and the Tk thread shows frames on their pts clock (pause/speed shift the clock; `loop` resets it). **Sound:** `decode_clip_audio()` decodes the AAC track once per clip to 16-bit stereo PCM at 44.1 kHz (~55 ms for 30 s); `ClipAudio` plays it with stdlib `winsound` (`SND_FILENAME | SND_ASYNC`); winsound can't play from memory asynchronously, so the PCM from the current offset is written to `clips\_sound0.wav` / `_sound1.wav` (alternating so the file the previous sound holds is never rewritten). `ClipPlayer._sound_from(pos)` restarts sound and re-bases the video clock together on first frame, loop, resume, speed and sound toggles; pause/close/`_start` stop it. `0.5×` = WAV at 22,050 Hz. One sound app-wide (`ClipAudio.owner`). Settings keep the old keys `emote_hd` / `emote_sound` plus `locker_type`. `av` is optional (`import av` in try/except); without it the play button opens the clip in the browser. `_detail_reset()` closes the player.
- **Packaging:** `release.yml` installs `av` and bundles `docs/data/locker`. PyAV's FFmpeg DLLs push the exe from ~19 MB to ~47 MB; a frozen test decoded frames fine (PyAV 19 + PyInstaller 6). The `.bat` launcher installs `requirements.txt` if `PIL` or `av` is missing.
- **Ideas:** style variants (`video-<idx>.mp4`, style names need the item page), desktop hover previews, favorites / owned list per type, music packs (audio on item pages), cars / instruments / LEGO types, pitch-preserving slow motion, volume control (would need `waveOut` via ctypes).

## 7. Web demo architecture (`docs/`)

- **No framework, no build, no dependencies.** Only one external origin: fortnite-api.com.
- `app.js` is one IIFE. `state` holds items, shop, filters, per-mode grid state (`sections`, `flat`, `selected`, `scroll`), layout and the `rendered` Map.
- **Virtual grid with DOM diffing:** `layout()` computes rows/positions like the desktop app. `render()` keeps a `Map` of rendered nodes keyed by tile index or `h<row>` for headers, removes nodes out of range, and appends new ones (with 400 px `OVERSCAN`). Scroll is throttled by `requestAnimationFrame`, resize via `ResizeObserver`. Tiles are absolutely positioned inside `#gridInner`.
- Tile size shrinks so phones get at least 3 columns (`tileSize()`). Breakpoints: ≤1240px narrower panels; ≤980px sidebar becomes an off-canvas drawer and the detail panel a bottom sheet (`body.menu-open` / `body.detail-open`); ≤640px stacked toolbar.
- **Hash routing:** `#item/<cosmeticId>`, `#shop`, `#shop/<offerId>`. `history.replaceState` avoids history spam, and "Share link" copies `location.href`.
- **MD5 in JS:** a compact RFC 1321 implementation (`md5()`), cross-checked against Python `hashlib` (empty string, unicode, 55/56/64/200-byte boundaries). If you touch it, re-run that check.
- The **static "about" panel** in `index.html` is real visible content (SEO + first-visit pitch) shown when nothing is selected. Keep it accurate and don't hide keyword text (search engines penalize hidden text).
- `localStorage` keys: `fcb.size` (tile size) and `fcb.sprites.v1` (Sprite progress). Both accesses are wrapped in try/catch.
- Debug hook: `window.__fcb = { md5, webSlug, epicItemUrl, state }`.
- Headless Chrome screenshots: Chrome's minimum headless window width is about **500 px**, so phone-width screenshots look wrong. That's a tooling artifact, not a CSS bug.

## 8. Build, release, CI

- **CI** (`ci.yml`): `python -m py_compile fortnite_cosmetics_browser.pyw` + Sprite catalog validation + `node --check docs/app.js`. There are no unit tests yet (§13).
- **Release** (`release.yml`): on tag `v*` (or manual dispatch) it runs on `windows-latest` with Python 3.12, `pip install pillow pyinstaller`, then

  It zips exe + LICENSE + README and publishes the release with `softprops/action-gh-release@v2`, using `.github/release-notes.md` + auto notes.

- `--icon` paths resolve relative to `--specpath` if you pass one. Use an absolute path when building with a custom specpath (this tripped the local test build).

## 11. How it was tested (reuse these techniques)

- **Desktop smoke harness:** load the .pyw with `importlib.machinery.SourceFileLoader`, construct `App(root)`, schedule steps with `root.after(...)` (wait about 8-10 s for data), call methods directly (`set_mode`, `goto_cosmetic`, `goto_offer`, `set_tile_size`, `search_vars[...].set`), screenshot with `PIL.ImageGrab.grab(bbox)`, then `root.destroy()`. Print `root.winfo_rootx()`: **-32000 means the window is minimized** (the user or OS minimized it). Call `deiconify(); state("normal"); geometry("+0+0"); lift()` before grabbing, otherwise you get a black image.
- The user may click the test window while it runs. Unexpected selections or filters in screenshots can be human input, not bugs.
- **Web:** `python -m http.server 8765 --directory docs`, then headless Chrome `--headless=new --window-size=1440,900 --virtual-time-budget=30000-60000 --screenshot=...`. Big shop render images may still be loading at capture time; fortnite-api.com can be slow, it's not page weight (renders are ~85 KB).
- **URL formula check:** build URLs for every cosmetic and assert the known-good fortnite.com URLs are in the set (17/17).
- **Exe check:** `Start-Process` the built exe, wait about 12 s, read `MainWindowTitle` ("Fortnite Cosmetics Browser by 248Tech"), then stop it.
- **Editing pitfalls seen:** a `sed` "insert after line matching X" hit 3 identical lines and silently broke categories, so prefer exact-match Python replace scripts that assert `count == 1`. Very long bash heredoc chains failed with a quoting error; write files with the editor tool instead.

## 12. Known limitations and risks

- **Single upstream dependency:** if fortnite-api.com changes its schema, rate-limits, drops CORS or goes down, both apps break. The desktop app degrades to cached data; the web demo has no cache.
- **Web payload:** about 17 MB of JSON (gzip ~2-3 MB) on every visit, with no service worker or IndexedDB cache.
- **Hotlinked images:** all images come from fortnite-api.com. The project hosts no game assets (good for licensing; bad if they block hotlinking).
- **Legal:** fan project, not affiliated with Epic. Respect Epic's trademark and fan content guidelines: no Epic logos as our branding, keep the disclaimer, never sell game assets. The "FORTNITE" wordmark text in the UI is plain styled text, not Epic's logo; keep it that way.
- **Desktop accessibility:** the Tk canvas grid is invisible to screen readers.
- **Unsigned exe:** SmartScreen warnings; one-file PyInstaller exes are sometimes flagged by antivirus heuristics.
- Shop `tileSize` ignored; `legoKits` and other newer content arrays are not parsed (they show as "Offer").
- fortnite.com links for unverified categories, bundles and Jam Tracks fall back to search/shop pages.
- The desktop app counts on-demand cached thumbs only for browse thumbnails, so the "Icons cached" number is approximate until a prefetch finishes.
